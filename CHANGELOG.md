# Changelog

## Unreleased

### Behavior changes

- **SQL Server restores ordered backup chains to new databases.** `BackupToDedicatedDiskAsync` creates verified full, differential or log backups with an explicit copy-only policy. `PrepareRestoreChainAsNewAsync` pins native identities, validates differential bases and contiguous log ranges, and refuses changed recovery forks or file identities. `RestoreChainAsNewAsync` holds one target lock through all `NORECOVERY` steps and separate final recovery without command replay or `REPLACE`. Existing copy-only and single-full restore APIs remain available; capacity budgets, CHECKDB and application readiness stay explicit.
- **SQLite explicit command timeouts govern transaction startup.** An explicitly configured `CommandTimeout` now sets the connection default as well as individual commands, so provider-created BEGIN commands and ordinary table-copy writes honor it. `ResetCommandTimeout()` restores provider or connection-string defaults.
- **Commands execute once by default.** Queries, scalars, mapped results, reader startup and SQLite prepared commands no longer replay arbitrary SQL after a transient error. A result-returning batch can already have committed a write. `CommandRetryMode.ReplaySafe` explicitly enables retries on a client whose SQL and callbacks are all safe to repeat; `RetryNonQueryOperations` retains its nonquery-only opt-in. Neither retries individual commands inside transactions. Connection establishment retains its separate retry policy.
- **SQLite session and prepared cancellation interrupts statements outside transactions.** Canceled statements stop without waiting for completion, canceled writes roll back their statement, and the connection can run the next command. Explicit transactions retain cooperative cancellation to protect earlier writes. Sessions and their commands must be used sequentially.
- **Resource-pair cleanup attempts both disposals.** A failing transaction or reader disposer no longer prevents its connection or command from being disposed. When both disposers fail, the first exception is preserved.
- **Compound queries order and page the combined result.** Root `OrderBy`, `Limit`, `Top` and `Offset` are compiled after `UNION`/`INTERSECT`; SQL Server `TOP` limits the combined selection. Ordered or paged operands retain their local scope, nested operands preserve grouping and mixed operators compose from left to right across dialects. Compound mutations are rejected. SQL Server's zero limit returns an empty selection without emitting invalid `FETCH NEXT 0`.
- **Offset-only SQLite and MySQL queries use valid syntax.** The compiler emits SQLite's `LIMIT -1` or MySQL's unlimited-limit sentinel before `OFFSET`, returning all remaining rows.
- **Mixed union chains preserve correlation.** `UNION`/`UNION ALL` switches do not introduce unnecessary derived tables. MySQL/MariaDB compilation rejects explicit outer qualifiers when a grouped or locally paged operand would move them into an unsupported derived-table scope; local and nested internal aliases remain valid.
- **Raw source modifiers preserve local bindings.** Index hints, selected partitions, `STRAIGHT_JOIN`, ODBC table groups and MariaDB temporal clauses retain their aliases in grouped MySQL queries. Executable comments defer version-dependent correlation binding to the server. Shared query diagnostics recognize these modifiers without reserving otherwise valid SQLite identifiers.
- **Compound subqueries name explicit projections safely.** SQL Server and MySQL wrappers assign unique internal column names to unnamed or duplicate projections and preserve explicit result names by position. Unnamed expressions use stable generated names when required. MySQL uses scoped CTE column lists supported by MySQL 8 and MariaDB 10.2, preserving source references and local paging without rewriting raw expressions.

- **SQLite backups of WAL databases hold a snapshot.** `SQLite.BackupDatabase` and `Invoke-DbaXSQLiteMaintenance -Action Backup` used the step-wise copy, which restarts whenever another connection writes and so never completed on a database written continuously. They now pick the method from the source file header (`SqliteBackupMethod.Auto`): a WAL database is copied as a held snapshot (as `BackupDatabaseSnapshotAsync`), which completes while other connections write and contains the database as it was when the backup started, and a rollback-journal database keeps the step-wise copy, which never blocks its writers for longer than one step. `SQLite.BackupDatabaseAsync(source, destination, method, options, progress, cancellationToken)` and a `BackupDatabase` overload take the method explicitly (`Snapshot` or `Incremental`); `BackupDatabaseAsync` reports failures as `BackupDatabase` does (`DbaQueryExecutionException` without the paths, `IOException` for an existing destination), and `SqliteBackupResult.Method` reports the method used. `Invoke-DbaXSQLiteMaintenance` gained `-BackupMethod Auto|Snapshot|Incremental`, writes progress once per percent, stops the copy and removes the partial destination on Ctrl+C, adds `Destination`, `BackupMethod`, `CopiedPages`, `DestinationLengthBytes` and `Elapsed` to its `-PassThru` object for a backup, and rejects `-BusyTimeoutMs 0` for a backup with a parameter error (the provider already refused it).
- **Streamed timestamps retain UTC/local kinds.** Provider `DateTime` values keep their kind in detached rows and collected tables. When collected source columns use different timestamp modes, the result widens to `object` to preserve each value. Tabular conversion of `DataRow` or `DataRowView` inputs requires matching timestamp modes and rejects incompatible schemas instead of silently normalizing values.
- **Collected provider subtypes use safe object storage.** A runtime provider type differing from its declared column type uses `object` storage unless it is a built-in storage type, keeping the original value without requiring extra trimming metadata.

- **SQLite result column types follow the returned values.** Buffered SQLite queries (`Query`, `QueryAsync`, `Invoke-DbaXSQLite`) no longer take a column's type from the first row only:
  - A column that starts with NULLs adopts the type of its first non-null value, so `PRAGMA table_info` now returns `dflt_value` as `string` instead of failing.
  - INTEGER and REAL values in one column widen to `object`, preserving the original `long` and `double` values regardless of row order. REAL values were previously squeezed into a `long` column.
  - Any other mix becomes `object` and keeps each value as returned. For example, a TEXT column that later holds integers used to turn them into strings (`"10"`); now it holds `long` values, so code that casts, such as `(string)row["x"]`, should convert instead.
- **SQLite `DataRow` streaming can switch tables mid-stream.** `QueryStreamAsync`, `QueryStreamWithConnectionStringAsync` and `Invoke-DbaXSQLite -Stream -ReturnType DataRow` yield detached rows. When a later row needs a different column type, rows from that point belong to a new `DataTable` with the adapted schema, so do not assume every row shares the first row's `DataRow.Table`.
- **`-Stream` with `-ReturnType DataTable` or `DataSet` now returns rows.** `Invoke-DbaXSQLite`, `Invoke-DbaXMySql`, `Invoke-DbaXPostgreSql`, `Invoke-DbaXOracle` and `Invoke-DbaXQuery` used to return an empty table. They now return every streamed row in a table named `Table0`, with column types widened to hold every streamed value (the same rules as buffered SQLite results). An empty stream still writes nothing for `DataTable` and an empty `DataSet` for `DataSet`.
- **Streamed and `DataRow` results get unique column names.** Duplicate column names (`SELECT 1 AS a, 2 AS a`) in streamed rows and in buffered `ReturnType.DataRow` results are suffixed (`a`, `a1`) like buffered `DataTable`/`DataSet` results, instead of throwing `DuplicateNameException`. Names are compared case-insensitively, so `a` and `A` become `a` and `A1`.
- **The compile cache is bounded in size.** `CompileWithParameters` cached up to 1,000 statements keyed by their full shape, whatever their length, so long `IN` lists or raw SQL could hold tens of megabytes (25.7 MB retained after compiling 1,000 raw statements of about 10,000 characters of key and SQL plus 200 statements with 3,000-value `IN` lists; 8.3 MB now). The cache now also keeps at most `QueryCompiler.CacheCharacterLimit` characters of keys and SQL (about 8 MB), evicting the oldest statements first, and does not cache a statement whose key plus SQL exceeds `CacheEntryCharacterLimit` (16,384 characters; the key repeats the statement's text, so this is SQL of roughly 8,000 characters), which is compiled every time. `CacheCharacterCount` reports the current size.
- **Literal SQL keeps backslashes inside MySQL and PostgreSQL strings.** `Compile()` (without parameters) used to double only single quotes, so on MySQL, which reads a backslash as an escape by default, a value such as `x\' OR 1=1 -- ` ended its literal early. Text containing a backslash is now written as a `_utf8mb4 0x…` hex literal on MySQL and as an `E'…'` literal on PostgreSQL, which read back exactly whatever the server's escaping settings. Other text and other dialects are unchanged. `CompileWithParameters` was never affected.
- **Literal SQL refuses values it cannot quote.** `Compile()` used to write any value without its own literal form through `ToString()`, unquoted: a `char` quote, an enum name, a culture-formatted number or a PowerShell-wrapped string reached the SQL as code. `char` is now a string literal, enums their underlying number, integers use invariant formatting, `DBNull` is `NULL`, `DateOnly`/`TimeOnly` are quoted (.NET 8 or later builds), and any other type, NaN or infinity throws `NotSupportedException`; use `CompileWithParameters` for them. This includes types that used to produce usable text, such as `BigInteger`, `nint`, `Int128`, `Half` and `SqlTypes` values. `New-DbaXQuery` unwraps PowerShell-wrapped values (for example strings with note properties) before building the query, and treats a `DBNull` `-Where` value like `$null` (`IS NULL`).
- **Canceling a SQLite query stops the running statement.** Microsoft.Data.Sqlite checks the token only before a statement starts and `SqliteCommand.Cancel` does nothing, so a canceled long query used to run to completion. The asynchronous query, scalar, non-query, reader and streaming APIs now interrupt the connection they opened when the token is canceled, so a running statement ends with `OperationCanceledException` for that token within milliseconds, and an interrupted write is rolled back. `QueryReaderAsync` keeps its token attached until the reader is disposed. `SQLiteTableCopyAdapter` page reads, row counts and its autocommit destination commands (schema and clearing statements) stop the same way; transactional page writes are not interrupted. Not interrupted: statements on the client's own transaction connection (`useTransaction: true`), because an interrupted write would roll back the whole transaction; and a statement waiting for a lock, which stops when its busy timeout ends. `QueryStreamAsync<T>(database, …)` now validates the database path when called, like its connection-string sibling.
- **Literal SQL quotes `Guid`, `TimeSpan` and `byte[]` values.** `Compile()` (without parameters) used to emit `Guid` values unquoted and `byte[]` values as `System.Byte[]`. It now emits quoted GUID and time literals (`'[-][d ]hh:mm:ss[.fffffff]'`) and dialect hex literals (`0x…`, `X'…'`, `decode('…', 'hex')`, `HEXTORAW('…')`). `DateTime` literals are unchanged and still drop fractional seconds; use `CompileWithParameters` when precision matters.

### New features

- **SQL Server estimated query plans.** Capture and inspect SHOWPLAN XML through the shared structured plan model. Native identities and fractional output/read/cardinality estimates remain distinct from SQLite rules and statistics. Typed scalar parameter declarations produce explicitly generic estimates; capture isolates session state and preserves cancellation.
- **PostgreSQL estimated query plans.** Capture and import native EXPLAIN JSON through the shared plan model, with bound named values and existing Npgsql types. Owned read-only capture preserves active transactions, cancellation and cleanup errors without command replay. Output and cost estimates retain their native meaning; rows read and table cardinality remain unknown. PostgreSQL array subscripts and nested comments now preserve statement boundaries in shared splitting.

- **Result-bound typed mapping.** `DbaRecordMapper.Bind<T>(schema)` resolves property ordinals once per result, retaining the conversions, null behavior and struct support of `For<T>()`. Bind again after changing column layouts. Neither mapper retains a reader or connection; property conversion types are cached during mapper creation.
- **SQLite connection profiles span the operational APIs.** `SQLite.ConnectionOptions` and `SQLiteTableCopyAdapter.ConnectionOptions` apply a copied profile for pooling, read-only mode and pragmas across commands, sessions, transactions, bulk paths, diagnostics and copy checkpoints. The adapter's `ConfigureConnection` callback registers connection-local functions and collations on every read/write/preflight/checkpoint connection. Explicit method options override the profile; native backups retain their dedicated policy.
- **SQL Server workload evidence.** `GetQueryStoreStateAsync` reads actual/desired capture state, storage and read-only reasons; `GetIndexUsageAsync` reads bounded rowstore table-index counters, constraint roles, statistics and restart context. `SqlServerMonitoringScope.Workload` collects both through the existing monitoring snapshot with explicit truncation and optional-section failures. The PowerShell command forwards `MaximumIndexUsageRows`. Nullable counters and server-local timestamps retain their meaning; collection does not change Query Store or recommend removing indexes.

- **SQLite snapshot backup that completes while the database is written** (`SQLite.BackupDatabaseSnapshotAsync`). The source connection holds one read transaction across every step of SQLite's online backup, so the copy is the database as it was when the backup started and changes by other connections neither appear in it nor restart it; progress, cancellation, busy handling, atomic overwrite and cleanup work as in `BackupDatabaseIncrementalAsync`. Measured on a copy of a 14.55 GB WAL monitoring database written 6 times a second: 35 to 69 s over six runs on a shared machine (`PagesPerStep` 256 or 4096), with the writers' p95 latency unchanged (0.5 to 1.6 ms) and `PRAGMA integrity_check` and row counts of the copy matching the snapshot; at 60 writes a second it took 61 s and the WAL grew to 151 MB meanwhile. The step-wise `BackupDatabaseIncrementalAsync` restarted 1,080 times in 3 minutes under the same load and never passed 0.6%. `VACUUM INTO` also completed (248 s, 140 s of CPU, a 10% smaller file), and a file copy of the database and WAL under a held read took 8 s but is consistent only if no connection checkpoints meanwhile, which a library cannot ensure. In WAL mode the snapshot keeps checkpoints from moving later pages into the database file until the copy ends, and a `FULL`, `RESTART` or `TRUNCATE` checkpoint run meanwhile waits for the checkpointing connection's busy timeout, with writers behind it; in rollback-journal mode the snapshot is a shared lock that keeps writers from committing, so use the incremental backup there (a rollback-journal database written continuously needs WAL to be backed up online).
- **SQLite planner statistics** (`SQLite.ReadPlannerStatisticsAsync`, `SQLite.WritePlannerStatisticsAsync`, `SqlitePlannerStatistics`). Reads and writes the rows of `sqlite_stat1` as typed values (table rows, average rows per key prefix of each index, SQLite's option words), so a small test database plans like a production-sized one: copy the statistics from a large fixture, or write chosen ones; `replaceAll` with no rows removes them all, after which SQLite assumes about a million rows per table. A written row replaces the row of the same table and index (names compare without case, as SQLite matches them), reading returns the row the planner uses, and a row with option words must give every key column of an existing index a count (SQLite would read missing ones as unique). The write runs in one transaction, creates `sqlite_stat1` when missing (`ANALYZE sqlite_schema`) and changes the schema version, so connections that are already open, pooled ones included, reload the statistics with their next statement that reads the database. The bundled SQLite is built without `SQLITE_ENABLE_STAT4`, so `sqlite_stat4` is neither written nor read.
- **SQL statement splitter** (`SqlStatementText.Split(sql)` for SQLite, `Split(sql, dialect)`). Returns the statements of a script, each from its first token to its last, without separators and without the comments between statements. Semicolons inside strings, quoted and bracketed identifiers and comments do not split, nor do those in the `BEGIN … END` body of an SQLite `CREATE TRIGGER` (a `CASE … END` or a column named `end` inside it does not end it) or, for PostgreSQL, in dollar-quoted bodies (`$$ … $$`, `$tag$ … $tag$`, which are parameter names in SQLite). MySQL and T-SQL procedural bodies and scripts that rely on `GO` are not kept whole. `IsSingleStatement` now uses it, so an SQLite trigger with a body counts as one statement, and `ExplainQueryPlanAsync` explains the one statement without the semicolons and comments around it (`;SELECT 1` is accepted, a comment-only text or one whose statement starts with `EXPLAIN` after a comment is refused).
- **Query plan guard** (`SQLite.ExplainQueryPlanAsync`, `DbaQueryPlan`, `QueryPlanAssert`, `QueryPlanRules`, `SqlSargabilityAnalyzer`, `SqlStatementText`). `ExplainQueryPlanAsync` returns SQLite's `EXPLAIN QUERY PLAN` for one statement as typed steps (scan, search, automatic index, temporary B-tree with its purpose, virtual table) with the table and index; aliases from `FROM`, `JOIN`, comma lists and `UPDATE` are resolved to table names, schema prefixes are dropped, `LEFT-JOIN`/`RIGHT-JOIN` steps are read, and a step that names an alias used for several tables counts as reading each of them. The classification errs toward scans: SQLite prints full index scans and one-row aggregates alike, as an unconstrained `SEARCH`, so such a step is a scan unless it is a `MIN`/`MAX` lookup that reads one end of an index: the statement looks up one column of one table (also inside `COALESCE`/`IFNULL` or a subquery), the index (or `WITHOUT ROWID` primary key, or rowid) serves every term of its `WHERE`, the column is the index column after the equalities or the one a range bounds, and the index orders it under the column's own collation; such a step (constrained or not) is a one-row search; virtual tables read without an index and reads of co-routines and materialized CTEs are scans too (name the large tables so those do not count). Steps carry the rows `sqlite_stat1` expects (`EstimatedRows`: a scan's table rows, or the average rows per key of the index columns a search's equalities cover; `TableRows`) and whether a search is a range open on one side (`IsOpenEndedRange`). `QueryPlanAssert.Check` lists violations (full scans; wide searches, which read more than `WideSearchFraction`, a tenth, of a large table's rows by the statistics or search a range open on one side, unless a `LIMIT` stops them (the step is the first of its query; nothing sorts or groups all rows first, and a sort of the last `ORDER BY` terms only while the index reads a range of the first whose values hold few rows by the statistics; the query reads one table; each term of its `WHERE` is a bare comparison, without arithmetic, sign or call on a column (on values they are fine), `NOT`, subquery, pattern or `IN` list, of columns the index search constrains, or a keyset seek on the `ORDER BY` columns that names the first while the index reads a range of it; and the query has its own `LIMIT` without an aggregate or `GROUP BY`, or is an `EXISTS` subquery), so the latest rows of one key read in index order and keyset pages (also under a collation; not keys by expression) pass, while a filter the index does not serve fails them; temporary B-trees over rows read in full or by a wide search, so a top-N `ORDER BY … LIMIT` over a non-selective key fails; automatic indexes on named large tables; and by default a named table that appears in no step, so typos fail closed); `NoFullScan` and `UsesIndexes` throw `QueryPlanViolationException` with the SQL and plan, without depending on a test framework. `SqlSargabilityAnalyzer.Analyze` is a documented heuristic over SQL text that reports functions (DbaClientX's `dbx_lower`/`dbx_upper` included) and `::` casts around columns in `WHERE`/`JOIN ... ON` conditions, a `COLLATE` applied to a comparison with a column (`Name COLLATE NOCASE = @p`, or `Name = @p COLLATE NOCASE`) unless `SqlSargabilityOptions.ColumnCollations` (or `DefaultCollation`, `BINARY` by default) says the column's index uses that collation (`IS [NOT] NULL` is never reported), and leading-wildcard `LIKE`/`GLOB` patterns; `SqlSargabilityOptions.Functions` adds other registered functions. A function is reported when a column appears anywhere in its arguments (`ABS(@p - Seen)`, `dbx_lower(NULLIF(Name, ''))`), outside subqueries and date parts, and the outermost known function is the one finding, its inner calls part of it (so `instr(dbx_lower(Name), @p)` is reported as the `instr` call); a `COLLATE` after a call or parentheses around a column (`CAST(Name AS TEXT) COLLATE NOCASE = @p`) is reported as a collation as well as the function. Each finding names its `Column` and, where the statement shows it, its `Table` (through the qualifier's alias, or the one table an unqualified column's query reads), and its message says which. A plan API for SQL Server is not included.
- **SQLite trigram search indexes** (`SQLite.CreateTrigramIndexAsync`, `RebuildTrigramIndexAsync`, `DropTrigramIndexAsync`, `SQLiteTrigramSearch`). Creates an FTS5 trigram index holding a copy of chosen text columns, kept current by triggers that remove entries by rowid and follow updates through any rowid name or generated column (so `INSERT OR REPLACE` cannot corrupt it), after checking that the key is the table's rowid. `SQLiteTrigramSearch.MatchingKeys(index, text, params columns)` returns a parameterized key query for `WhereInRaw`, with the text quoted as an FTS5 phrase so operators and quotes in it are matched literally; it searches all indexed columns, one, or a chosen set (an FTS5 column filter with each name quoted), and an overload takes several texts and finds rows containing any of them. Matching ignores case with SQLite's Unicode folding and needs at least three characters (`CanMatch`). On 1,000,000 rows a rare text is counted in 5 ms instead of 189 ms and a common one in 144 ms instead of 287 ms; the index adds 128 MB for three short columns and makes inserts about 20 times slower, and "does not contain" and first pages of common text stay faster as scans. `RebuildTrigramIndexAsync` recreates the index and its triggers (after renames or lost triggers), and it and `DropTrigramIndexAsync` refuse a table that is not a trigram index, whatever the case of its name.
- **SQLite connection configuration and Unicode case folding** (`SQLite.ConfigureConnection`, `SQLiteUnicodeText.Register`). `ConfigureConnection` runs for every connection the client opens to run SQL (queries, streams, readers, transactions, sessions, `OpenDbConnection`, integrity checks, maintenance pragmas and diagnostics), so a consumer can register functions and collations once. `SQLiteUnicodeText.Register` adds `dbx_lower`/`dbx_upper` (invariant .NET case mapping) and the `DBX_NOCASE` collation (ordinal order of the invariant lower-case text, matching the .NET `ToLowerInvariant` folding the HtmlForgeX engines use) where SQLite's `lower()`, `LIKE` and `NOCASE` fold ASCII only. The collation compares the stored UTF-8 bytes in place instead of the two strings per comparison that the provider's `CreateCollation` marshals: a full sort of 1,000,000 rows by a short ASCII text took 2.2 s and allocated 3.3 GB before, 1.0 s and nothing now (non-ASCII text: 3.5 s and 2.7 GB before, 1.6 s now; a `BINARY` sort takes 0.6 to 0.8 s). Built-in `lower()`/`upper()` are left alone: replacing them on a pooled connection breaks them for the next user. The mapping follows the running runtime's case tables, so `REINDEX` an index or column built with them after moving to a runtime with different tables.
- **Safe "contains" conditions** (`WhereContains`, `OrWhereContains`, `WhereContainsRaw`, `OrWhereContainsRaw`). Matches text anywhere in a column or expression with `LIKE … ESCAPE '!'`, escaping `%`, `_`, `!` and, on SQL Server, `[`, so every character of the text matches itself; the text is always a parameter (or a quoted literal with `Compile`). A `TextFolding` argument chooses the case rule: `None` follows the column collation (a case-sensitive `instr()` on SQLite); `Database` folds both sides with the database's `LOWER` (`ILIKE` on PostgreSQL; SQLite's `lower()` folds ASCII letters only); `Invariant` folds every letter as .NET's `ToLowerInvariant` does, on SQLite only, through `dbx_lower()` (register `SQLiteUnicodeText`; other dialects throw `NotSupportedException`: their `LOWER` folds Unicode letters under a Unicode-aware collation or locale). The `caseInsensitive` overloads map to `None` and `Database`. `dbx_lower()` runs in .NET for every row: counting matches in 1,000,000 rows took 290 to 350 ms for ASCII values (160 to 210 ms with `Database`) and 490 to 590 ms for values with letters beyond ASCII (220 to 310 ms with `Database`, which misses their other case). SQLite uses `instr()` for every folding, ignoring the column collation: its `LIKE` ignores ASCII case unless `PRAGMA case_sensitive_like` is on, stops at NUL characters and refuses patterns over 50,000 bytes. Measured twice on the same 1,000,000 rows (ASCII and other letters, rare and common text, each folding), `instr()` was as fast as or faster than an escaped `GLOB '*text*'` in every case, typically by 5 to 15%. In the first run, `instr(lower(x), lower(@p))` took 160 to 260 ms where `LOWER(x) LIKE LOWER(@p)` took 220 to 270 ms on the same scans, and a plain `x LIKE @p`, which folds ASCII itself, 120 to 160 ms (15 to 50% less than `instr(lower())` in both runs) but with the limits above.
- **Negated conditions** (`Query.WhereNot(q => …)`, `Query.OrWhereNot(q => …)`). Wraps the conditions the callback adds in `NOT (…)` for every dialect, with values kept as parameters. The callback must add at least one complete condition and nothing else. Rows whose inner condition is unknown (a NULL comparison) match neither the condition nor its negation; to include them, group the negation with the NULL test (`BeginGroup().WhereNot(…).OrWhereNull(column).EndGroup()`), since `AND` binds tighter than `OR`. The safe operator list also accepts `NOT GLOB`, `NOT REGEXP` and `NOT RLIKE`. The compiler now rejects a `WHERE` token type it does not know instead of silently leaving it out.
- **Public identifier quoting** (`SqlIdentifier.Quote(SqlDialect, string)`). Quotes one table, column or alias name the way the query compiler does (`[a]]b]`, `` `a``b` ``, `"a""b"`), for raw fragments built from mapped or user-supplied names; a dot is part of the name. NUL characters, empty names and, for Oracle, double quotes are rejected with `ArgumentException`. The compiler and the SQLite and PostgreSQL bulk helpers now use it, so a name with an empty dotted part (`a..b`) or a NUL character, an Oracle name with a double quote, or an undefined `SqlDialect` value fails when compiled instead of in the database.
- **Read-only SQLite streaming** (`SQLite.QueryReadOnlyStreamAsync<T>`). Streams mapped rows from a `Mode=ReadOnly` connection, holding one row at a time: writes fail with `SQLITE_READONLY`, a missing file is reported instead of created, and canceling the token interrupts the running statement (.NET Standard 2.1 or later).
- **Prepared commands on SQLite sessions** (`SQLiteSession.Prepare`, `SQLiteSession.PrepareInsert`, and the same on `SQLiteAsyncSession`). A statement is prepared once on the session's connection and transaction, and each `ExecuteNonQuery`/`ExecuteScalar` (or async) call only rebinds values by position. Use it inside `RunInTransaction` to write many rows quickly and atomically. `PrepareInsert` quotes the table and column names. `null` is stored as NULL, enums as their underlying integer, and a wrong value count throws `ArgumentException`. Dispose the command before the session ends.
- **Keyset and offset paging** (`KeysetPagination`, `OffsetPagination`, `QueryPage<T>`). Keyset page queries refuse `Compile()`; compile them with `CompileWithParameters`. Cursors are unsigned by default: declare key types and set `SigningKey` when cursors come from untrusted clients. A key can carry a collation (`KeysetColumn.WithCollation`, a plain name of letters, digits and underscores, quoted on PostgreSQL) or be a trusted SQL expression (`KeysetColumn.Expression(expression, resultColumn)`, for example SQLite's `+"Seen"` so an index does not choose the order), applied in both the seek condition and `ORDER BY`; `KeysetPagination(pageSize, sortKeys, uniqueKey)` names the unique tie-breaker. The last key must be a plain column without a collation (an expression or collation can make different rows equal), and cursors are bound to the collation and expression, while cursors of plain keys keep their binding.
- **`SqlServer.UseDateTime2ForDateTimeParameters`** sends `DateTime` parameters as `datetime2` instead of `datetime`.
- **Typed streaming helpers.** `DbaRecordMapper.For<T>()` maps rows to public writable properties by column name; `DBNull` sets `null`, or the default for non-nullable value types, overriding property initializers. Date and time values without an offset are treated as UTC when mapped to `DateTimeOffset`, and `DateTimeOffset` values or text with an offset map to UTC `DateTime`. `DbaRecordMapper.Values()` maps rows to `object?[]`. `ChunkAsync` batches streams, and `SQLite.QueryStreamWithConnectionStringAsync<T>` streams typed rows from a connection string, so options such as `Mode=ReadOnly` work (both need .NET Standard 2.1 or later; not net472).
- **`Invoke-DbaXSQLite -ReadOnly`** opens the database with `Mode=ReadOnly` for buffered and streamed queries: statements that modify it fail with `SQLITE_READONLY`, a missing file is reported instead of created, and in-memory databases are rejected. File-backed connection strings retain their provider options; only `Mode` and `Pooling` are overridden for read-only access. Explicit options take precedence over file-URI query hints. Conflicting source aliases are rejected, ordinary filenames may contain option-looking text, and validation honors `ErrorAction`. Connection options are excluded from confirmation and error targets. SQLite may still create `-wal`/`-shm` files next to a WAL database, and `VACUUM INTO` can write other files.
- **Query execution helpers.** `Query.CompileWithNamedParameters(dialect)` and `QueryParameters.ToDictionary(values, dialect)` produce parameter dictionaries keyed by the compiled placeholders (`@p0`, or `:p0` for Oracle). `KeysetPagination.StreamAsync` and `ReadPagesAsync` read a whole result through keyset pages with memory bounded by the page size (.NET Standard 2.1 or later). Floating-point NaN, mixed numeric storage types and text, GUID, binary or provider-specific keys require `CompareKeys` to match database ordering.
